## User requirements

- **Arrange takes a mathematical graph and settings.** State positions, manual bends, portal offsets, start-view geometry, and outside-image positions belong to the editor drawing. With the same graph and settings, dragging nodes, bending edges, and arranging again must produce the same drawing. Group membership is input when retained. Disregard previous groups removes it from the input. Use stable ordering and deterministic tie breaks.
- **Preserve planarity through the final drawing.** The user identifies this fixture as planar. Keep a feasible embedding intact through coordinate placement, overlap handling, routing, and any cleanup. Count actual rendered curves and distinguish shared endpoints from intersections farther along incident edges. Include reciprocal edges, self-loops, and parallel lanes in the visual check.
- **Keep the main graph radial and compact.** Keep ordinary unobstructed edges straight. Prefer short local branches and avoid long detours, wiggles, or unnecessary bends. Equal angular spacing is a soft preference for small isolated stars where moving the leaves keeps spokes straight. Dense graphs should retain natural attachment angles.
- In subgroups, prefer external-state images on the left and internal flow to the right, subject to planarity and clearance. Keep external images independent from their original states. Reciprocal arrows use opposite physical sides. Self-loops should use clear sectors and stay clear of incident wires. Place comments after nodes and routes using available space. Comments do not influence the embedding or angular spacing.
- Keep the interaction responsive. Arrange already runs in a worker, but worker isolation alone does not solve the long wait. Preserve the existing interactive canvas performance and FSM semantics. Focus on Radial Compact first. The user has reported Tree problems separately.

## Current pipeline and likely failure mode

- `src/core/layout-topology.js` strips drawing geometry and applies the result back to the editor document. `src/editor/layout-task.js` sends the topology to `src/core/layout-worker.js`, which calls `solveLayout` in `src/core/smart-layout.js`.
- `planarCoordinates` in `src/core/planar-layout.js` tests the simple undirected skeleton with Topoloom and can produce a straight-line grid embedding via `planar-grid.js`. Parallel, reciprocal, and loop decorations are added by later routing. In `place`, the main radial layout mainly uses the embedding to order branches and then rebuilds coordinates with `radialTree` in `tidy-tree.js`. That ordering is a hint, so the resulting coordinates are not guaranteed to realize the same embedding. Subgroup candidates also use `compactPlanar` and other heuristics.
- `arrangeTopology` may call `untangle` on the ungrouped drawing. `repairRadialCrossings` then probes many coordinate changes around crossing endpoints and reroutes the entire graph for each viable probe. `shortenLocalBranches` and subgroup compaction can also trigger full routing. Repeated work in the repair path is a likely cause of the long runtime. Measure it separately from embedding, placement, and final routing.
- `computeRoutes` in `src/core/layout.js` chooses curves using local obstacle and label scores. It does not globally constrain every final edge to its embedding corridor. `crossingPairs` samples curves at 16 intervals and excludes shared-endpoint pairs, loops, and portals from its routed count. It can miss tangles that are obvious on screen. The user's hypothesis is that overlap resolution breaks planarity. The code confirms that placement and routing both have opportunities to lose planarity, but the exact first stage responsible for each artifact still needs to be traced. There is no verified single overlap pass to blame.

## Proposed implementation plan

1. **Measure the pipeline before changing it.** Run both fixtures with the exact settings above and record timings by stage. Record straight-skeleton crossings, final routed crossings, node and edge clearance, total and longest local edge lengths, bend count, and drawing bounds. Capture the stage where each annotated problem first appears. Repeat after scrambling coordinates and bends to verify identical output.
2. **Carry an explicit planar embedding into placement.** Keep the cyclic order of incident skeleton edges and choose an outer face deliberately. Start from a valid realization, such as the existing planar grid or a branch/block construction that realizes the same order. For the large radial hub, give branches and cyclic blocks contiguous sectors when the embedding allows it. Within sectors, keep local neighbors close. Use a deterministic choice of orientation and placement.
3. **Optimize with feasibility constraints.** Try bounded changes that improve radial shape, compactness, and edge length. Accept a change only if it preserves cyclic order, clearance, and the planar realization. Reserve enough room for parallel lanes, reciprocal arrows, and loops. Resolve overlap by adjusting feasible coordinates or available space within the embedding. An unconstrained final push-apart pass would undermine this model.
4. **Route inside the embedding.** Keep straight segments where clear. Give each skeleton edge a corridor and place reciprocal lanes on opposite sides within it. Allocate loops to clear sectors. Move labels independently when possible. Place comments last in the remaining space. Verify the rendered curves, including incident edges away from the shared endpoint, with a stronger intersection check than the current sampling alone.
5. **Remove the expensive repair loop once the constrained path works.** Use cheap geometric checks to reject candidates before routing, cache or update only affected local geometry where practical, and bound search deterministically. Retain a feasible solver-generated candidate as a fallback if a prettier candidate fails. For nonplanar inputs, minimize unavoidable crossings and keep the same aesthetic priorities. Never fall back to the saved drawing.
6. **Verify through the app.** Compare the annotated areas at readable zoom in both grouped and ungrouped views. Confirm deterministic output, no newly introduced crossings on the planar fixtures, a material runtime improvement, and unchanged transitions and lexer results. Run lint, build, and focused domain checks. The user will do most manual acceptance testing.
